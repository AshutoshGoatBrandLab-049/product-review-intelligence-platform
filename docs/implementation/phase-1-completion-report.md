## 7. Exact Local Schema Used

```sql
CREATE TABLE ingestion_watermarks (
  platform                          TEXT PRIMARY KEY CHECK (platform IN ('flipkart','myntra')),
  last_seen_source_id               BIGINT NOT NULL DEFAULT 0,
  last_reconciliation_run_at        TIMESTAMPTZ,
  last_reconciliation_rows_scanned  INTEGER,
  last_reconciliation_rows_changed  INTEGER,
  status                            TEXT NOT NULL DEFAULT 'idle' CHECK (status IN ('idle','running')),
  lock_acquired_at                  TIMESTAMPTZ,
  updated_at                        TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE normalized_reviews (
  canonical_review_id  CHAR(32) PRIMARY KEY,
  platform             TEXT NOT NULL CHECK (platform IN ('flipkart','myntra')),
  source_product_id    TEXT NOT NULL,
  source_review_id     TEXT NOT NULL,
  source_row_id        BIGINT NOT NULL,
  identity_confidence  TEXT NOT NULL CHECK (identity_confidence IN ('native','derived')),
  brand TEXT, rating SMALLINT NOT NULL CHECK (rating BETWEEN 1 AND 5),
  title TEXT, review_text TEXT,
  review_date DATE NOT NULL, review_timestamp TIMESTAMPTZ,
  date_confidence TEXT NOT NULL CHECK (date_confidence IN ('exact','day','month')),
  author TEXT, helpful_count INTEGER, not_helpful_count INTEGER,
  verified_purchase BOOLEAN, has_images BOOLEAN, image_urls TEXT[],
  size_purchased TEXT, color_purchased TEXT, country TEXT, product_url TEXT,
  content_hash CHAR(64) NOT NULL, source_updated_at TIMESTAMPTZ NOT NULL,
  source_extra JSONB, mapper_version INTEGER NOT NULL,
  ingested_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (platform, source_product_id, source_review_id)
);
CREATE INDEX idx_normalized_reviews_platform_product ON normalized_reviews (platform, source_product_id);
CREATE INDEX idx_normalized_reviews_review_date ON normalized_reviews (review_date);

CREATE EXTENSION IF NOT EXISTS pgcrypto;
CREATE TABLE identity_anomalies (
  anomaly_id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  canonical_review_id   CHAR(32) NOT NULL REFERENCES normalized_reviews(canonical_review_id),
  platform              TEXT NOT NULL,
  previous_content_hash CHAR(64) NOT NULL,
  new_content_hash      CHAR(64) NOT NULL,
  detected_at           TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE ingestion_rejects (
  reject_id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  platform           TEXT NOT NULL,
  source_row_id      BIGINT, source_product_id TEXT, source_review_id TEXT,
  reason             TEXT NOT NULL,
  failed_fields      JSONB NOT NULL,
  first_seen_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_seen_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  occurrence_count   INTEGER NOT NULL DEFAULT 1
);
```

`ingestion_rejects.failed_fields` is restricted at the application layer to the typed `FailedFieldKey` allowlist (5 keys) — never full review text, author, or raw payload.

## 8. Production Database Queries Executed

The **entire** production query surface consists of exactly 4 hardcoded functions in `src/database/prodReadOnly/index.ts`, backed by 2 repo files:

- `getFlipkartReviewsPage(afterId, limit)` → `SELECT <fixed columns> FROM "DataWarehouse".flipkart_reviews WHERE id > $1 ORDER BY id LIMIT $2`
- `getFlipkartReviewsByDateWindow(windowStart, afterId, limit)` → same table, `WHERE review_date >= $1 AND id > $2 ORDER BY id LIMIT $3`
- `getMyntraReviewsPage(afterId, limit)` → equivalent query against `"DataWarehouse".myntra_reviews`
- `getMyntraReviewsByDateWindow(...)` → equivalent date-windowed query against the same table

Plus two diagnostic-only statements used solely by the canary: `SELECT current_user, current_database()` and `SELECT 1`.

**No production database was actually reachable or queried in this session.** `backend/.env`'s `DB_PROD_HOST` is empty; `src/config/index.ts` deliberately defaults an empty value to the literal string `"unset.invalid"` rather than silently falling back to something reachable — this is an intentional fail-loud safety default (§45–58 in `config/index.ts`), confirmed by running `npm run canary` just now, which failed with `getaddrinfo ENOTFOUND unset.invalid` on every check. All query shapes above were exercised only against `pri_test_prodsource`, a local fixture database whose schema was built to mirror the verified production column shapes (`flipkartReviewsFixture.sql`, `myntraReviewsFixture.sql`).

## 14. Crash/Restart Results

`tests/integration/crashRecovery.test.ts` (3 tests, passing) proves: a lock left in `running` state by a simulated crash is recognized as stale after `STALE_LOCK_MS` (1 hour) and can be re-acquired; a watermark's `last_seen_source_id` only advances in the same transaction as the batch insert, so a crash mid-batch leaves the watermark at its pre-batch value with no partial advancement; re-running after a simulated crash reprocesses exactly the un-advanced rows, producing no gaps and no duplicate `normalized_reviews` rows (enforced by the `UNIQUE(platform, source_product_id, source_review_id)` constraint).

---

## 15. Idempotency Results

`tests/integration/trackB.test.ts` "PROOF: unchanged reviews cause zero writes on a second pass" — running Track B twice against unchanged fixture data yields `rowsInserted: 0`, `rowsUpdated: 0` on the second pass. `tests/integration/trackA.test.ts` confirms re-running Track A with an unchanged `last_seen_source_id` yields zero new inserts. `tests/integration/e2e.test.ts` runs a full Track A → Track B cycle twice and asserts no growth in row count on the second pass.

---

## 16. Duplicate Results

Enforced structurally by `normalized_reviews`'s `UNIQUE(platform, source_product_id, source_review_id)` constraint plus the deterministic `canonical_review_id` primary key (`SHA-256` over `[platform, sourceProductId, sourceReviewId]`, collision-safe via `JSON.stringify` encoding — verified in `tests/unit/canonicalId.test.ts`, 6 tests). Track A/B both use Sequelize upsert semantics keyed on this identity, so re-ingesting the same source row is a no-op, never a duplicate row.

---

## 17. Checkpoint Results

`tests/integration/checkpointLocking.test.ts` (5 tests, passing): a second concurrent run attempt while a lock is held throws `LockHeldError`; the lock releases on successful completion; a stale lock (older than `STALE_LOCK_MS`) is reclaimable; `last_seen_source_id` and `last_reconciliation_run_at`/`rows_scanned`/`rows_changed` are only persisted on commit, never on a failed/rolled-back run.

## 22. Known Limitations

- No HTTP/API layer exists yet — `app.js`/`server.js` are pre-existing empty stubs from the initial scaffold, unrelated to Phase 1's scope (ingestion pipeline only, no frontend/API per the explicit exclusion list).
- `canary.ts`'s line/branch coverage (56.86%/16.66%) is lower than the rest of the codebase because its failure branches are exercised by manual/standalone runs rather than asserted unit tests (see §13).
- Flipkart's `date_confidence` remains a `day`/`month` heuristic approximation, not a precise reconstruction — this is an accepted, documented architectural limitation carried over from Phase 2.6, not something Phase 1 could resolve (the underlying relative-date text was never persisted upstream).
- Track B's reconciliation window boundary (rows right at the 70-day edge) is tested for correctness of the window formula but the "excludes older reviews" test documents the boundary rather than asserting hard exclusion, since the seeded fixture data happens to fall inside the window either way (see the test's own comment in `trackB.test.ts`).

## 23. Remaining Risks

- **Untested at production scale.** All crash-safety, idempotency, and performance proofs are structurally sound and unit/integration-tested, but only against small local fixtures. The first real run against production-scale row counts (tens of thousands to millions of reviews) should be treated as a first-of-its-kind event, not a formality — watch actual query latency, transaction duration, and lock contention.
- **Production role grants unverified from this environment.** Layer 1 depends on the DBA having actually provisioned `review_intel_ro` as SELECT-only on exactly the two approved tables. This repo cannot self-verify that; it can only fail loudly if it's wrong (canary + Layer 3 static scan + Layer 2 fixed surface).
- **No production connectivity was exercised at all in this session** — meaning even the "happy path" of connecting to production has never actually been proven end-to-end yet. The first real connection attempt (once `DB_PROD_HOST` is set to a real value) should be treated as a checkpoint, not an afterthought — run `npm run canary` manually and review its output before any real ingestion run.
